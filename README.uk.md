# lyrics-semantic-search

Семантичний пошук текстів пісень: dense-пошук за ембедингами, lexical-пошук
(BM25) і їхній гібрид, злитий за рангом, а не за сирим скором. Офлайн-
пайплайн індексації та онлайн-обслуговування запитів, побудовані і
заміряні наскрізно на реальному корпусі ~30 тис. пісень.

## Можливості

- **Взаємозамінні ембедери** через реєстр ім'я -> фабрика: `bge-m3`
  (багатомовний, `max_seq_length=8192`), `e5-base`, `fasttext-avg`
  (статичні вектори), `tfidf` (без жодного завантаження моделі) —
  перемикаються конфігом, без змін коду.
- **Два бекенди індексу**: `numpy` (точний перебір за косинусом) та
  `faiss`.
- **Три режими пошуку**: `dense`, `lexical`, `hybrid` — гібрид зливає
  обидві гілки через Reciprocal Rank Fusion (RRF), а не зважену суму
  скорів (див. [Обґрунтування рішень](#design-rationale)).
- **Кешований офлайн-пайплайн**: `ingest -> preprocess -> embed ->
  index`, кожна стадія пропускається, якщо вже свіжа для свого конфігу,
  кеш-ключі ланцюжаться так, що зміна вище за течією інвалідує все нижче,
  `--force` обходить кеш.
- **Functional core, imperative shell**: логіка перетворення тексту —
  чисті функції без I/O (`core/`); файли, GPU, мережа — лише в
  `runners/`. Дешеве, швидке, детерміноване юніт-тестування прямо
  випливає з цього поділу.
- **Жоден фільтр не викидає запис мовчки** — кожен відхилений
  запис/чанк фіксується в `rejects.jsonl` із причиною із закритого
  переліку.
- **100% покриття тестами в `core/`**, включно з property-тестами на
  `hypothesis` (алгебраїчні властивості RRF, ідемпотентність чанкування/
  дедуплікації/нормалізації) поряд зі прикладними юніт-тестами — 266
  тестів загалом.
- **Повністю синтетичний демо-корпус** — 200 оригінально складених пісень,
  без завантажень, без GPU, будується й шукає за секунди на будь-якій
  машині.

## Швидкий старт (синтетичний демо-корпус)

Без реальних даних, без завантаження моделі, без GPU — `tfidf` +
`numpy` + `hybrid`, лише CPU:

```bash
pip install -r requirements.txt

# Генерує 200 синтетичних пісень і одразу запускає повний пайплайн
# побудови (записує в data_demo/demo/):
python scripts/generate_demo_corpus.py

# Пошук:
python -m lyrics_search.runners.search --config configs/demo.yaml \
  "sunrise valley" --data-root data_demo
```

Деталі — `configs/demo.yaml` і `scripts/generate_demo_corpus.py`;
опис рішення — `notes/reports/spec04-report.md`, §3.

## Налаштування для повного корпусу

Потрібно лише для реального корпусу `dev`/`full`, нейромережевих
ембедерів (`bge-m3`, `e5-base`, `fasttext-avg`) або бекенду індексу
`faiss` — демо вище нічого з цього не потребує. Дефолтний wheel `torch`
на PyPI може не відповідати вашій версії CUDA, тож спершу поставте його
з індексу PyTorch під вашу платформу/CUDA, а тоді решту:

```bash
pip install "torch>=2.6" --index-url https://download.pytorch.org/whl/cu124
pip install -r requirements-full.txt
```

## Архітектура

**Офлайн (build):** `ingest -> preprocess -> embed -> index`, на вході
один конфіг, на виході — директорія корпусу (`<data_root>/<corpus>/`).
Кожна стадія пропускається, якщо її артефакт на диску вже свіжий для
поточного конфігу стадії; `input_hash` стадії — це `cache_key`
*попередньої* стадії, тож повторний запуск ранішої стадії інвалідує все
після неї, навіть якщо конфіги пізніших стадій не змінилися. `--force`
безумовно обходить усі перевірки свіжості — єдиний спосіб відновитися
після зміни *коду* стадії без жодної зміни в конфігу.

**Онлайн (search):** суто на момент запиту. Будь-який стан
(підігнаний ембедер, індекс, довідники чанків/пісень) лише
*завантажується*, ніколи не підганяється й не будується — онлайн-гілка
звіряє `fitted_state_sha1` і `dim` проти власного `meta.json`
офлайн-гілки, а не довіряє наосліп. Прогрівний виклик `encode()`
відбувається одноразово під час завантаження в обох гілках, бо без
нього перший реальний виклик коштує ~476 мс замість ~40 мс для кожного
наступного.

## Конфігурація

Один YAML-файл повністю описує один запуск (`ExperimentConfig`,
валідується pydantic, `extra="forbid"`, тож одруківка падає гучно):

```yaml
corpus: dev              # dev | full | demo
chunking: sections        # sections | whole_song
embedder: bge-m3           # просте ім'я, або ім'я + params:
# embedder:
#   name: fasttext-avg
#   params:
#     vectors_path: data/models/fasttext/cc.en.300.vec
index: numpy               # numpy | faiss
retrieval:
  mode: hybrid              # dense | lexical | hybrid
  rrf_k: 60
  top_k: 50
  return_n: 10
```

`load_config()` додатково звіряє `embedder.name`/`index` з іменами,
зареєстрованими в реєстрі на цей момент, і `embedder.params` — з
переліком обов'язкових параметрів цього ембедера, тож незареєстроване
ім'я або відсутній обов'язковий параметр (наприклад, `vectors_path` у
`fasttext-avg`) падає ще на етапі завантаження конфігу, а не десь
всередині запуску build/search. Реальні приклади на всі комбінації
ембедер/індекс/режим — `configs/*.yaml`.

`chunking` — водночас і компонент шляху, тож артефакти обох гілок лежать
поруч, а не витісняють одне одного. `raw.jsonl` лишається в корені
корпусу, бо інжест — єдина стадія, яка не залежить від чанкування:

```
data/<corpus>/raw.jsonl
data/<corpus>/<chunking>/chunks.jsonl
data/<corpus>/<chunking>/embeddings/<embedder>/
data/<corpus>/<chunking>/indexes/<embedder>/<index>/
```

`whole_song` дає рівно один чанк на пісню. Він придатний лише для
`bge-m3`, у якого реальний `max_seq_length` — 8192; жоден інший ембедер
тут не вмістить цілу пісню в один вектор.

## Оцінювання

На вході конфіг і набір запитів, на виході таблиця метрик — лише online,
тим самим кодовим шляхом, яким іде `search`, по одному запиту за раз:

```bash
python -m lyrics_search.runners.eval --config configs/full_dense_faiss.yaml \
  --eval-set data/eval/queries.jsonl [--json-out results.json]
```

Набір запитів — це JSONL, один запис на запит. Записи з ключем `_meta`
пропускаються, а не оцінюються. `relevant_song_id`, якого немає в
корпусі, валить завантаження з називанням id та його рядка — знайти його
неможливо в принципі, тож у результатах він був би невідрізнимий від
промаху пошуку.

```json
{"query": "...", "relevant_song_ids": ["a1b2c3d4e5f6a7b8"], "query_type": "..."}
```

Recall@{1,5,10}, MRR та nDCG@10 (`core/metrics.py`, чисті функції)
звітуються загалом і по кожному зрізу, разом із `n` та bootstrap-довірчим
інтервалом — малий зріз не може показати значущу різницю, і саме інтервал
робить це видимим у таблиці, а не постфактум. Зрізи ріжуться за
властивостями *релевантних* пісень запиту, а не того, що повернулося, —
тож два ретривери завжди оцінюються на одному й тому ж розбитті:
`split_by` × `force_split`, `is_translation`, `query_type` і жанр. Запит,
релевантні пісні якого не збігаються за властивістю, потрапляє в кошик
`mixed`, а не приписується до однієї зі сторін і не викидається, — тож
`n` кожного виміру й далі дає в сумі загальну кількість.

Жанр береться з `data/<corpus>/genre.jsonl`, який один раз будує
`scripts/build_genre_lookup.py` і не читає більше ніщо в пайплайні — це
метадані для аналізу, а не вхід пошуку. За відсутності файлу зріз
пропускається з друкованою приміткою. Значення — це власна колонка `tag`
вихідного датасету, а не класифікація, зроблена тут.

## Обґрунтування рішень

Повне обґрунтування й посилання на код/тести для кожного пункту —
`notes/decisions/retrieval-design.md`.

**1. Злиття: RRF за рангами, не зважена сума скорів.** Косинусна
подібність (dense) і BM25 (lexical) лежать у непорівнюваних шкалах, які
неможливо коректно об'єднати без калібрування на кожному корпусі окремо
— BM25 необмежений і залежить від розміру корпусу, косинус обмежений
у [-1, 1]. Будь-яке фіксоване зважування мовчки віддавало б перевагу тій
гілці, яка на конкретному корпусі видає більші сирі числа, а не тій, що
насправді релевантніша. RRF натомість зливає за *рангом*, який за
побудовою інваріантний до шкали:

```
score(d) = сума за ранжованими списками r, що містять d, від 1 / (k + rank_r(d))
```

**2. Dense — по дедуплікованих чанках, lexical — по цілому `text_raw`.**
Навмисно різна гранулярність, не недогляд: буквальний збіг ключового
слова будь-де в пісні — значущий лексичний сигнал, навіть якщо
відповідний фрагмент прибрала внутрішньопісенна дедуплікація на рівні
чанків, тож перечанкування для BM25 просто викинуло б реальний recall
без жодної користі. Перебудова BM25 із сирого тексту під час
завантаження — дешева й детермінована: нічого переоптимізовувати.

**3. Агрегація чанк -> пісня за MAX, не за середнім.** Середнє карало б
довгу пісню за кілька нерелевантних куплетів, навіть коли один чанк —
сильний збіг: наприклад, пісня з 6 чанками, з яких один на 0.9, а п'ять
близько 0, усереднилася б до ~0.15 і програла б коротшій, посередній,
але рівномірній пісні з одним чанком — хоча саме вона містить
найкращий фрагмент-збіг у всьому корпусі. Максимум зберігає суть
питання пошуку: "чи є в цій пісні хоч десь сильний збіг".

**4. Переклади позначаються, не відсіюються.** Ймовірні
сторінки-переклади текстів визначаються й фіксуються (`is_translation`),
але ніколи не відхиляються — переклад лишається валідною версією тексту,
доступною для пошуку, для користувача, якому вона потрібна, і
позначення замість видалення зберігає цей вибір для подальших
споживачів, не звужуючи корпус мовчки.

**5. Міжпісенні дублікати з ідентичним текстом не зливаються.** Пісні
з побайтово ідентичним текстом під різними метаданими артиста/назви
(кавери, live-версії, акустичні версії — 19 груп / 38 записів, 0.13%
повного корпусу, всі перевірені вручну й підтверджені як справжні) лише
позначаються для видимості, але не зливаються: користувач, що шукає
конкретний кавер, може цілком легітимно хотіти побачити його окремо від
оригіналу, а не мовчки згорнутим в один результат.

## faiss на Windows: не-ASCII шляхи

Власні `write_index()`/`read_index()` у faiss викликають `fopen()`
напряму на переданому шляху. На Windows цей шлях відкриття файлу
ненадійно обробляє не-ASCII байти — будь-який шлях робочої копії, що
містить нелатинські символи (саме так це й було виявлено), спричиняє
тихі збої або невиразний C++ `RuntimeError`. Обробку шляхів усередині
faiss неможливо виправити з боку Python; її можна лише обійти.

Обійдено в `lyrics_search/indexes/faiss_index.py` тим, що власне
збереження/завантаження faiss за шляхом узагалі не викликається:
`serialize_index()`/`deserialize_index()` конвертують індекс у/з
`bytes`-буфера в пам'яті цілком усередині C++-шару faiss (жодного
доступу до файлової системи з боку faiss), а власне файловий I/O виконує
звичайний Python `open()` — який на Windows коректно обробляє
Unicode-шляхи. Повний опис:
`notes/decisions/faiss-nonascii-path-windows.md`.

## Продуктивність

**Офлайн (побудова повного корпусу, `bge-m3`, RTX 3050 Laptop 4 ГБ
VRAM, fp16, batch 16):** 30 000 пісень -> 208 411 згенерованих чанків,
181 471 залишилось після препроцесингу. Ембединг: ~14 хв за чистих
умов (848–860 с); прогін в умовах конкуренції за GPU з іншими
застосунками показав 23 хв (1378 с). Пікове використання VRAM
1388 МіБ. Результат: 355 МБ векторів на диску (181 471 x 1024,
float16).

**Онлайн (запит, після `warmup()`), те саме залізо, індекс `numpy`:**

| Стадія | Час |
|---|---|
| Завантаження моделі (з прогрівом CUDA/cuDNN) | 9.98 с |
| Середній перший запит (модель завантажена й прогріта, 5 різних запитів) | 53.2 мс |
| Середня латентність повторного запиту | 55.6 мс |

Ціль <100 мс для повторного запиту досягається із запасом (пошук по
181 тис. x 1024 float32 векторів: ~32 мс; `encode()` моделі на GPU:
~21 мс). Латентність запиту чутлива до контенції за GPU з боку інших
застосунків на спільному лаптопному залізі — повний опис замірів і
застережень — `notes/reports/spec03-patch-report.md`.

## Тестування

```bash
pip install -r requirements.txt
pytest -q                                                    # весь набір
pytest -q --cov=lyrics_search.core --cov-report=term-missing # покриття core/
```

266 тестів загалом. З базовим `requirements.txt` 261 проходить і 5
пропускаються: 3 потребують `faiss-cpu` (з `requirements-full.txt`);
інші 2 потребують реальної збірки корпусу `data/dev` та файлу
fasttext-векторів — це реальні дані, навмисно виключені з git (див.
[Дані та авторське право](#дані-та-авторське-право)), тож ці 2
пропускаються на будь-якому свіжому клоні незалежно від того, який
requirements-файл встановлено. `lyrics_search/core/` — шар чистих
функцій перетворення — має 100% покриття рядків в обох випадках, включно
з property-тестами на `hypothesis` для алгебраїчних властивостей RRF та
ідемпотентності чанкування/дедуплікації/нормалізації тексту.

## Дані та авторське право

Тексти пісень — це матеріал, захищений авторським правом. `data/`
(реальні dev/full корпуси) ніколи не комітиться — публічними є лише
код, конфіги, метадані та повністю синтетичний демо-корпус. Винятки в
`.gitignore` вузькі й явні: `data_demo/**/*.jsonl` (лише оригінально
складені демо-тексти) та `tests/golden/**/*.jsonl` (короткі синтетичні
фікстури, не реальні тексти пісень).

Реальний корпус будується під час виконання з
[`mrYou/lyrics-dataset`](https://huggingface.co/datasets/mrYou/lyrics-dataset)
на Hugging Face Hub (`lyrics_search/sources/hf_dataset.py`) — цей проєкт
його не поширює й не вендорить: `ingest` завантажує датасет у власний
HF-кеш користувача. Перед використанням перевірте умови самого датасету;
тексти в ньому належать відповідним правовласникам, а не цьому проєкту
чи автору датасету. Жанрові мітки для зрізів в eval — це власна колонка
`tag` того датасету, а не класифікація, зроблена тут.
